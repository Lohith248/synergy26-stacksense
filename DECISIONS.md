| D6a | D6 re-confirmed 12 Nov 2026: `cloud_preference: none` = no public cloud; `any` already means the engine may choose a provider. `none` with `managed_cloud` or `self_hosted_cloud_vm` is `infeasible`, and the message tells the user how to resolve it: choose `any` if public cloud is acceptable, or a deployment model that keeps the stack on their own infrastructure (`on_premise` / `air_gapped`). | D12a | D12 approved with a narrower rule (replaces D12's keyword inference): `infrastructure.residency_country` is used when supplied. Otherwise the description pins a country only when one sentence explicitly states a data-residency requirement for a single country (e.g. "Customer data and backups must stay in Canada"); the output cites that sentence. A mere location mention ("Our team is based in Toronto") is a hint only. Hints, ambiguous wording or conflicting requirements keep the critical unresolved-residency warning. A clear country with no verified eligible region for the requested provider is flagged as a conflict. | Avoids pinning data on incidental place names while still honouring an explicit requirement. | approved by the participant 12 Nov 2026 (narrower rule) |
| D14 | Lossless input coercion (amends D3): an integer-valued float is accepted for an integer field (`30000.0` is read as `30000`), and a number equal to a listed `requirements.availability` value is accepted as that string (`99.9` is read as `"99.9"`). Each use is recorded in `assumptions` and as an `INPUT_COERCED` info warning. Nothing else is coerced: case differences, numbers written as strings, unknown enum values, booleans as strings and lists of the wrong type stay `invalid_input`. | No valid input is rejected for notation alone, while the statement (p4: lower-case strings exactly as written) is not loosened for anything that is a different value. | participant, 13 Nov 2026 |
