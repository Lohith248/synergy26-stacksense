| D13 | Right-sizing gates for supporting services (E3): a supporting service sized for scale or latency the input does not state is not added, and the output says so (an alternative on the replacing component plus a `SERVICE_NOT_ADDED` info warning that quotes the input values). Thresholds, all planning heuristics kept in `engine/rightsize.py` (not vendor limits, not knowledge-base data): dedicated game servers need a fast-action genre word or `requirements.p95_latency_ms` <= 100 and no turn-based wording; the analytics warehouse needs `scale.data_volume_gb_12_months` >= 100 for `data_analytics` (>= 200 when inferred from description words), otherwise BI runs on the application database; a CDN needs a public audience (not "used only by employees"; an `internal_tool` only with `seo_critical` or multi-region/global users); a CRDT sync server needs description evidence of simultaneous editing of one item (the type `realtime_collab` alone is not enough, games never); Supabase counts as PostgreSQL for native full-text search at tier <= 1. | D14 | Lossless input coercion (amends D3): an integer-valued float is accepted for an integer field (`30000.0` is read as `30000`), and a number equal to a listed `requirements.availability` value is accepted as that string (`99.9` is read as `"99.9"`). Each use is recorded in `assumptions` and as an `INPUT_COERCED` info warning. Nothing else is coerced: case differences, numbers written as strings, unknown enum values, booleans as strings and lists of the wrong type stay `invalid_input`. | No valid input is rejected for notation alone, while the statement (p4: lower-case strings exactly as written) is not loosened for anything that is a different value. | participant, 13 Nov 2026 |
| D15 | A gap in the knowledge base is never a critical hard-constraint failure (E45). `PAYMENT_DATA_LOCATION` and `LLM_REGION_CHECK` are `warning`s that state what the knowledge base verifiably knows (for Stripe under `data_residency` `eu`: Stripe Payments Europe, Limited is a party for EEA processing; transfers to Stripe, LLC rely on the EU-US Data Privacy Framework and Standard Contractual Clauses; that is a transfer mechanism, not an EU-only storage commitment) and the next action (check the DPA; an acquirer whose DPA commits to EU storage if data must stay in the EU). A gap alone leaves `status` at `ok_with_warnings`, adds no `Relaxed:` assumption and no "Relaxed recommendation" prefix; a `Payments:` assumption records how the residency was applied. Facts come from `research/R17-eu-payments.md` (13 Nov 2026); the Data Privacy Framework listing stays `official-unverified`. | The statement allows an `ok_with_warnings` answer to carry warnings; calling an unverified vendor location a critical conflict, and then saying the stack "does not satisfy" the constraint, is false for a stack that sits in the required region. | proposed 13 Nov 2026; participant confirmation pending |
| D16 | Over-engineering guard (E12; `engine/overeng.py`, `THRESHOLDS`, all planning heuristics): (1) **Static-eligible.** The backend and database are `None` and hosting is a static host when `requirements.auth` is `none`, there is no realtime, file storage, multi-tenancy, ML, mobile or API-only platform, the workload is not `write_heavy`, there are no existing systems, the deployment is `managed_cloud`, compliance has no `hipaa`/`rbi_localisation`, and the description names no stored-user-data or server-side work (accounts, log-in, shop, forum, database, uploads, payouts, ledger, KYC, chat, SMS/OTP, scheduled jobs and similar). Payments no longer force a backend when the description names a hosted payment button or link ("donation button", "payment link", "hosted checkout"). Types `content_site` and `other` qualify; `web_app` and `internal_tool` only when the description is editorial (blog, brochure, documentation, news, opening hours). Other types (shop, SaaS, marketplace, API, ...) never. High traffic alone never adds a backend or database: the output says the CDN serves pre-built pages, quotes the inputs, and states when to add one ("add a backend when accounts, stored user data or server-side payments appear"). (2) **Budget floor.** Below the 'large' scale tier, an optional add-on whose cheapest estimated tier costs more than 15% of `budget.monthly_infra_usd` (a budget of 0 treats any paid floor as too large; same 15% as the earlier Azure Front Door rule) gives way to a cheaper option the knowledge base already holds, and the output says so (`SERVICE_NOT_ADDED` info plus an alternative): managed cache is not added (unless `realtime` needs its backplane), dedicated search becomes database full-text search, a managed queue becomes a database-backed job queue, the AWS/Google Cloud CDN becomes the free Cloudflare plan (unless that cloud is explicit). When the stack still exceeds the budget the existing `BUDGET_EXCEEDED`/`BUDGET_AT_RISK` warning is unchanged. (3) **Small team.** For a team of 5 or fewer, ML `inference_api` on a Node.js, Java or C# backend loads the exported ONNX model in-process (vendor-documented ONNX Runtime bindings, source `onnxruntime-languages`, `official-unverified`) instead of a separate Python service, so the style is not `service_oriented`; other backends keep the separate service and the text says why. On-premises Kubernetes (k3s) needs a team above 5 as well as DevOps at medium scale. None of the three rules ranks core layers against each other except by switching a site to static. | Claude proposed it on 13 Nov 2026 from the statement's edge-case table ("Over-engineering traps": simple stacks, no microservices or Kubernetes without justification). **proposed, participant confirmation pending** |
| D17 | Cost realism (E8). Every figure in the cost band is a printed line; figures not in `kb/sources.json` are labelled `planning estimate` or `planning heuristic` in the text, and all the tables live in `engine/costreal.py`. (a) A device count in the description sizes IoT ingestion even without a reporting interval (one message per device per 60 s is assumed and said); a write-heavy IoT volume that also uses object storage is half append-only database rows at database SSD rates; a self-run database's disk is a line, and an existing database's growth is named as outside the band. (b) Managed ML training is never below a floor from `scale.data_volume_gb_12_months` (20-80 GPU-hours per TB a month at the knowledge-base GPU rate, for volumes of 100 GB and up) and such an output never carries `BUDGET_FAR_ABOVE_NEED`. (c) On-premise and air-gapped outputs carry one line, `Hardware (indicative, not a quote)`: servers per scale tier (plus a standby for an availability target, a tooling server for a team of more than 3, a GPU server for ML, disks above 500 GB), amortised over 36 months, up to 30% more at the upper bound; the participant answered Q4 (`add the indicative line`). When only this line pushes the minimum over the budget, `BUDGET_EXCEEDED` is a warning, not critical, and says that servers already owned lower the new spend. (d) Per-message lines scale with users and a stated assumption: phone OTP (0.3-1.0 logins a month, as before), e-mail (4-8 sends per recipient, recipients from a stated list size else every user, $0.10-0.60 per 1,000) and LLM tokens (5-20 questions per user, 3,000 input + 400 output tokens; the line is the larger of this and the tier table). When the budget is far below the minimum (critical `BUDGET_EXCEEDED`) the message names the dominant line and what to cut; nothing is removed from the stack. A single line above 10 times the budget gets an explicit `Sanity check` sentence. (e) When `scale.peak_concurrent_users` is absent the peak is users x a documented fraction, never above users: 10% as before, 5% or 2% (interactive or read-mostly) when the description counts a monthly audience; the ratio used is written into `assumptions`. Deviations from the brief: data_analytics and time-series-rule outputs with object storage keep object-storage rates (the storage layer exists because files do); the video-call and maps lines stay on the tier table. Outputs of P1-P6 are unchanged. | A cost band that prints $0-0 for a hardware deployment, a fixed table for per-message services, a 10%-of-readers peak or a training line with no relation to the data volume looks precise and is wrong; naming every assumption lets a reader change one and see the band move. | proposed 13 Nov 2026; participant confirmation pending |
